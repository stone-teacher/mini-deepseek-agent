# AI 辅助开发与问题解决记录

## 项目概述

“小航”是基于 Python 和真实 DeepSeek API 实现的最小 CLI Agent。项目自行实现 Agent Loop、工具注册与调用、会话管理、基础上下文处理及执行日志，不依赖 LangGraph、OpenHands、OpenClaw 等 Agent 框架。

开发过程中使用 AI 辅助需求拆解、接口分析、代码示例、问题诊断和测试构建；开发者负责代码录入与调整、方案确认、环境配置和运行验证。以下按工程任务整理代表性 Prompt 与实现结果。

## 1. 核心架构与模型接口

### 任务 Prompt

> 基于最小可用 Agent 的要求，设计职责清晰的 Python 项目结构。将 CLI、Agent Runtime、LLM 客户端、工具系统、SessionStore 和 ContextManager 分离，明确模块间的数据流。通过统一接口支持 FakeLLM 与真实 DeepSeek 客户端替换，使核心循环不依赖具体模型实现，并控制抽象层级和依赖数量。

### 实现决策

- CLI 负责配置、输入输出和会话切换；Runtime 负责模型请求、工具执行及循环终止。
- 使用 LLMClient 协议定义 complete() 的消息输入、工具输入和统一响应。
- DeepSeekLLMClient 负责内部对象与 API 格式转换，使用 OpenAI-compatible SDK 完成网络通信。
- FakeLLM 按顺序返回预设响应，用于构造确定性的离线测试。
- 采用同步 CLI 和进程内存储，优先完成题目要求的核心闭环。

### 验证

真实模型完成普通文本回答；相同 Runtime 分别使用 FakeLLM 和 DeepSeekLLMClient 跑通工具调用流程。

## 2. 工具协议与调用执行

### 任务 Prompt

> 设计包含工具名称、描述、参数 Schema 和本地 handler 的注册机制。模型依据 Schema 返回工具名和参数，Runtime 负责查找与执行。明确内部参数字典与 API JSON 字符串的转换，以及工具调用 ID 在请求和结果之间的关联方式。实现 calculator、mock search 和 todo，避免工具职责超出项目范围。

### 实现决策

- ToolRegistry 提供 register、get 和 list_specs。
- ToolSpec 保存工具名称、描述、JSON Schema 和 handler；发送到模型的描述不包含本地函数对象。
- 使用 json.dumps / json.loads 转换工具参数，并将响应整理为 AssistantResponse 和 ToolCall。
- calculator 采用 AST 白名单，支持指定算术运算、数学函数及常量。
- search 查询内置固定文档；todo 管理当前会话的待办记录。
- todo handler 通过闭包绑定当前 Session，模型无需传入或选择内部会话对象。
- todo 的 complete 表示状态更新，实际任务执行由 Agent 与相应工具承担。

### 验证

真实 DeepSeek 生成 calculator 调用，Runtime 执行后通过 tool_call_id 回传结果。表达式 `(12345 + 67890) * 321` 得到 `25755435`，最终模型回答与工具结果一致。

## 3. 会话隔离与连续对话

### 任务 Prompt

> 以用户和会话的组合标识管理状态，保证同一用户的不同窗口以及不同用户之间互不影响。切回已有会话时复用历史和待办状态。检查纯对话追问与工具追问是否获得必要的历史信息，并明确进程内会话的生命周期。

### 实现决策

- SessionStore 使用 `(user_id, session_id)` 作为字典键。
- Session 分别保存消息历史和 todo 当前状态。
- CLI 的 /session 命令切换当前会话对象，不触发模型请求。
- Runtime 为每次输入绑定当前 session 的 todo 工具。
- 同一会话的历史随后续请求发送，支持“刚才的结果”等引用。

### 验证

- CLI 窗口一创建“完成 README”，窗口二查询为空，切回窗口一后待办仍然存在。
- 自动测试检查不同用户、不同窗口的消息和待办隔离，以及同一会话对象复用。
- 真实工具追问先计算得到 36，再根据“把刚才的结果除以 5”生成 `36 / 5` 调用，得到 7.2。
- 纯对话中说明项目名“小航”和语言 Python，后续追问能正确回答；离线测试检查第二次请求确实包含前一轮对话。

## 4. 上下文组织与基础压缩

### 任务 Prompt

> 检查上下文构造是否保留系统提示、近期对话和必要状态。对超长旧历史采用确定性的基础压缩，验证文本量是否实际减少。分析按消息条数截取对工具调用协议的影响，避免丢失工具请求或对应结果，并明确压缩与原始会话存储之间的边界。

### 问题与处理

**问题一：减少消息条数不等于减少上下文体积。**

初版将旧消息全文拼接成一条摘要，文本量并未减少。调整为限长摘录：选取旧历史末尾最多 6 条消息，每条最多保留 120 个字符并按需加省略号，整段摘录不超过 600 个字符。

**问题二：截取位置可能落在工具交互中间。**

直接保留最后 N 条消息，可能只留下 tool 结果而丢失 assistant 的调用请求。调整为将切分位置向前移动至该轮 user 消息，保留近期完整轮次。

### 验证

- 测试确认长历史处理后的总文本量减少，系统提示和近期消息保留。
- 未完成 todo 加入压缩后的上下文提示，已完成 todo 不加入该提示。
- 原 Session 历史不因构造请求而被修改。
- 对一条 assistant 请求两个工具的情况，即使保留目标为 1 条消息，仍保留用户消息、调用请求和两个工具结果。

### 取舍

当前方案是有损摘录，可能丢失早期细节；字符阈值是触发条件，不是严格的总请求 token 上限。完整近期轮次和待办状态可能使请求继续超过目标预算。相关限制在 README 中说明。

## 5. 参数校验、异常与日志

### 任务 Prompt

> 区分响应解析失败、工具参数不合法、未知工具和 handler 执行异常。对当前工具使用的 Schema 规则进行本地校验，确保非法参数不会触发执行。将工具失败转成可回传给模型的结果，记录调用 ID、工具名称及执行状态，并使用循环次数上限防止持续调用。

### 实现决策

- 在 handler 执行前检查必填字段、额外字段、字符串类型和枚举。
- 对未知工具、校验错误和执行异常生成 tool_error 消息，关联原调用 ID 后继续循环。
- 日志覆盖工具开始、成功、失败及异常类型。
- 每次用户输入默认最多调用模型 8 次，超限返回明确提示。
- API 和响应解析异常由 CLI 捕获并显示错误类型；当前不执行自动修复重试。

### 问题与验证

| 场景 | 处理与证据 |
|---|---|
| expression 传入数字 | 校验返回 ValueError；测试确认 calculator handler 未执行 |
| calculator 执行 1 / 0 | 捕获 ZeroDivisionError，保存并回传工具错误，记录失败日志 |
| 请求未注册的 weather | 注册表返回 KeyError，错误进入下一次模型请求 |
| 模型持续请求工具 | 限定两次模型调用的测试确认恰好调用两次，随后返回上限说明 |
| 工具日志未显示 | 核对发现 CLI 已配置 logging，但 Runtime 未产生对应记录；补齐后使用固定工具调用验证 |
| 工具参数 JSON 不完整 | 解析器明确拒绝；同时检查合法 JSON 但非对象的参数及空 choices |

## 6. 测试策略与验证依据

### 任务 Prompt

> 将已观察的交互行为转化为可重复的离线自动测试。验证对象应包括实际工具结果、状态变化、下一次模型请求、调用次数与失败日志，避免仅凭 FakeLLM 的预设回答认定功能正确。使用真实 API 实验补充离线测试无法证明的模型行为。

### 测试策略

- 使用标准库 unittest，默认测试不访问网络、不需要 API key。
- 通过 FakeLLM 安排响应序列，覆盖正常、异常和循环上限路径。
- 使用 mock 记录接口调用；对正常计算保留真实 calculator 执行。
- 检查下一次请求是否包含工具结果或上一轮对话。
- 使用 assert_not_called 检查非法参数未触发 handler。
- 使用 assertLogs 检查失败记录。
- 修改公共模块后运行完整测试集，检查既有行为是否回归。

### 验证结果

截至文档整理时，最近一次开发验证中 12 个离线测试方法全部通过：

```text
Ran 12 tests
OK
```

运行命令：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

真实 API 实验已验证文本回答、工具调用闭环、工具追问及纯对话追问，并通过 CLI 观察会话切换和待办恢复。真实 API 验证为手动实验，未纳入默认离线测试。

测试数量不等同于代码覆盖率；当前没有声称达到完整覆盖或生产级可靠性。

## 7. 工程结论

- 模型提出工具请求，本地 Runtime 负责校验和执行，二者通过明确的数据结构连接。
- 工具描述、参数校验和工具内部业务约束分别承担不同职责。
- 最终答案正确不足以证明工具链正确，需要检查执行结果和回传消息。
- 会话隔离依赖对象归属与存储键，而不是仅靠系统提示约束模型。
- 上下文压缩需要同时考虑文本量、状态保留和工具消息结构。
- AI 辅助开发的建议以源码检查、离线测试和实际 API 输出进行复核。
